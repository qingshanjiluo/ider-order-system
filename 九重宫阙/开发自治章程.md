## 附：R12 · 内容真源与追加纪律（轮103，含一次真实数据事故）

### R12.1 真源澄清（覆盖不变量 3 的旧表述）

不变量 3 原文写"内容数据 = `data/*.js` 纯定义 + 台账"，**与当前实现不符**，据实修正：

- **真源 = 存档 `data/game.db`**（`col_*` 表）。改内容 = 改存档。
- `src/data/*.js`（如 `world-lore.js`）与 `src/data/content-export.json` 台账是**派生/只读锚点**，不是编辑入口。
- 改内容的正确闭环：**改存档 → `node src/scripts/content-sync.js export` → `npm run verify:rebuild` → `node scripts/gate.js`**。
- 直接编辑 `content-export.json` 会在下次 export 时被覆盖，且 `verify:rebuild` 会判红。

### R12.2 `getNextId` 误用事故（轮103 实锤，23 只原有怪被顶掉）

- **现象**：新增 48 只怪全部拿到 id 1..48，**覆盖了灵兔/竹妖/火焰蜥蜴王等 23 只原怪**（无报错、无崩溃，只有对账时才暴露）。
- **根因**：`getNextId(collection)` **只接一个参数**（集合名）。写成 `getNextId(db, 'monsters')` 时第一个参数成了 db 对象，函数静默返回 `1`。
- **恢复**：`git checkout -- data/game.db` 回滚，再按正确顺序重跑投产链。
- **防复发（三重静态锁，已入 P7 玩法闭环套件）**：
  1. 任何脚本用两参写法 `getNextId(x, ...)` 直接判红；
  2. `seed-content.js` / `fix-recipes.js` 新增前必须查 id 占用，占用即 `exitCode=1` 拒绝覆盖；
  3. 存档怪 id 与台账逐条对账，id 相同而名字不同 = 顶掉旧数据，判红。
- **通用规则**：**内容追加一律用「表内最大 id + 1」，禁止用行数或集合长度推 id**（id 有历史空洞，行数 ≠ 最大 id）。

### R12.3 追加内容必须守住数值池（否则会静默改坏难度）

内容追加会改变"按池统计量"算出的机制结果。轮103 三次实锤，均已修并各写一条锁：

| 事故 | 现象 | 修法 |
|---|---|---|
| 池水位被拉低 | 各境界池「最硬/中位」从 1.60 涨到 2.24~6.38（原有 Boss 突然"超线"） | 新怪/抬级怪的血量**必须按所在境界池中位**配，不按等级线性推算 |
| 同图血量断层 | 火焰山 425~3337（7.9 倍），同一张图里忽而被秒忽而秒怪 | `rebalance-pool.js` 图内补血，迭代收敛 |
| 大限劫对手变弱 | 选敌锚是「池内实时中位」，新增怪拉低中位 → 合体/渡劫应劫从必败变必胜（0%→100%） | 保留「贴池中位 + 有界台阶」规则，给中位加「境界期望血量」护栏 |

- **纪律**：**任何内容追加后，必须重跑 `node scripts/rebalance-pool.js` 与 `node scripts/test-gameplay-loop.js`**，不得只看"测试原来绿的"就提交。
- **一键链**：`node scripts/run-content-pipeline.js`（seed → align → rebalance → dedupe → fix-recipes → fix-dangling-refs → export）。实测复跑**逐字节幂等**，是内容投产的唯一正确入口。
- **禁止**手工分步乱序跑（轮103 中途重复跑 rebalance 造成二次失衡，浪费一轮）。

### R12.4 递归改引用的纪律（`fix-dangling-refs` 第二起事故）

- **现象**：脚本递归改写任意 JSON 数字，把 `monsters.level_range = [46,55]` 里的 55 当成物品 id 改写，导致怪等级越出地图区间。
- **修法**：三重防线 —— ① 只认语义外键名（`item_id`/`result`/…）；② 值域闸（只可能是 items 表里出现过的 id）；③ 字段黑名单（`level_range`/`stats` 等纯数字数组不进递归）。
- **纪律**：**任何递归改写脚本必须带事后自查**（本脚本已加：改完复验所有 `level_range` 仍在地图区间内，不合规即判红）。

## 附：R13 · 战斗数值的两条锁互相冲突（轮103 实测，待裁决）

### 现象（实测数字，不是推测）

`node scripts/sim-battle.js` 在**未做任何内容改动**的 HEAD 上就是红的：

| 段位 | 目标带 | HEAD 实测 |
|---|---|---|
| 段1 炼气~筑基 | 75-92% | **72.8% ✗** |
| 段2 金丹~元婴 | 60-78% | 77.4% ✓ |
| 段3 化神~合体 | 45-65% | **72.4% ✗** |
| 段4 大乘~渡劫 | 30-50% | **66.8% ✗** |

同时 `test-content.js` 的「双向 TTK 窗口」+「倒挂回归锁」另有要求：中位怪打死参考玩家 **>2.0 回合**、玩家击杀中位怪 **≤8 回合**。

### 冲突证明（可行域扫描）

对段4（大乘/渡劫）扫描 `攻击倍率 × 血量倍率` 共 36 个组合，逐组实测三条约束
（胜率落带 / 双方 TTK 达标 / 玩家不磨盘）：

- **可行解只有 1 个**（攻击 ×1.6、血量 ×1.0 → 胜率 46.0%），且**落在刀口上**：
  把同一组合换到 sim-battle 的口径下复测，胜率变成 55.7%（仍是红的）。
- 相邻组合全部非可行：稍微降攻击就"被秒"（TTK < 2.0），稍微加血量就"杀太慢"（>8 回合）。
- **加血量反而让胜率升高**（×1.5 → 63.9%）：因为 `runBattleLoop` 在 50 回合超时后按
  `attacker.hp > 0` 判攻方胜 —— 怪血越多越容易打满 50 回合，玩家"白赢"。
  这条超时口径让"血量"这个旋钮在高端段位是**反向**的。

**结论**：在**现有战斗公式 + 现有超时判定**下，"四段胜率带"与"TTK 窗口"在段4 上不能同时满足。

### 待裁决（三条路，各有代价）

1. **改超时判定**（推荐）：超时不再判攻方胜，改为按剩余血量百分比判或判平。
   代价：会影响所有战斗（含 PVP/副本），需要回归 E3 全部锁。
2. **放宽段4 目标带**（如 30-60%）：最省事，但等于承认"高段位玩家仍有优势"，与
   "随进度递减 = 难度曲线成立"的原始设计意图相悖。
3. **调玩家强度曲线**（`src/services/character.js` 的 `calculateAttack/HpMax`）：
   治本（玩家强是根因），但牵动 E3/E4/E9 三处数值验证与四张结算表，风险最大。

**在裁决前**：
- `scripts/calibrate-bands.js` 保留为**手动诊断工具**（`--dry` 只报数），
  **不接入** `run-content-pipeline.js` —— 自动跑会在两个约束间反复震荡并每轮改库。
- 门禁保持红（如实反映），不靠放宽阈值让它变绿。
- 已把标定与验收的测量代码统一到 `scripts/sim-battle-lib.js`（此前"各抄一份"导致
  element/暴击字段不一致，标定值与验收值差 20 个点，白折腾 8 轮）。
